# Tina 开源产品调研

把一个开源项目从“它做了什么”转换成“Tina 是否应该做、做哪一部分、用户能得到什么”，而不是复刻它的界面或代码。

## 适用与不适用

适用：

- 用户给出一个开源项目 / App / GitHub 仓库，问“这个功能能不能加到 Tina”。
- 需要从多个开源项目里筛选产品需求。
- 需要按 Tina 的 feature request 模板产出可直接提交的报告。

不适用：

- 单纯的代码审查、重构、性能优化。
- 已经明确要实现某个功能，只需写代码。
- 需要法律意见的许可证判断（本 skill 不评估 license）。

## 硬约束（逐条给结论，不能跳过）

| 约束 | 判定标准 |
|---|---|
| macOS 15 | 功能必须在 macOS 15 上可用。Tina 当前最低支持 macOS 14；如果功能依赖 15+ API，必须写出 14 上的降级/隐藏方案，或明确说明这是一次最低版本提升。 |
| 原生实现 | 优先 Swift / SwiftUI / AppKit / Objective-C。Electron、Node、Java、Python 运行时默认不合格；只有在能重写成小体量原生代码时才继续评估。 |
| 上游 Release 包（若有） | 被调研项目的最新 release 产物（DMG/zip/tar/单二进制）**≤30 MB 是适配性正面信号**；超过 30 MB 说明软件本身可能过重，默认 defer 或只取可独立剥离的小范围 MVP，除非能证明目标能力与体积无关。**没有 release 时跳过此项、不扣分**，改用源码/依赖/资源估算。Tina 自身的增量体积另算，是成本项。 |
| 复杂度 | 不引入新的特权 helper、系统扩展、DriverKit、网络服务或大规模状态机，除非用户价值足够高且风险有明确缓解。优先 MVP，避免 1:1 复刻。 |
| 不重复 | 先查 `Sources/Tina/Core/FeatureCatalog.swift`、`Sources/Tina/Services/`、`README.md` 和已有 issue；与现有功能重叠时必须说明“增强”还是“重复”。 |
| 用户价值 | 必须回答“上游产品解决了谁的什么痛点”和“Tina 用户多得到什么能力”，不能只列功能点。 |

## 工作流

1. **锁定调研对象**
   - 记录仓库 URL、默认分支、最新 release/tag、最近提交日期、主要语言、star 数（仅作参考，不当作价值结论）。
   - 用 `scripts/probe_macos_project.sh <repo>` 做静态探测：项目类型、部署目标、依赖、构建产物大小。

2. **还原产品而不是罗列代码**
   - 读 README、文档、release notes、关键 issue。
   - 按“用户任务 → 入口 → 行为 → 结果”拆成 3–8 个功能块。
   - 标出哪些是核心、哪些是边缘/平台特定/历史包袱。

3. **先过硬约束**
   - 逐项判定 macOS 15、原生、上游 Release 包体积、复杂度、重复。
   - 先看被调研项目有没有 release：没有就标记 `size: n/a` 并跳过，不要因此 reject。
   - 有 release 时记录资产实际大小（`gh release view --json assets`）；≤30 MB 是正面信号，>30 MB 是“可能过重”的负面信号。再单独估算 Tina 的增量（资源 X MB、依赖 Y、二进制 Z）。
   - 任一项“不合格”且没有可接受的替代方案，直接给出 reject/defer，不要继续堆功能描述。

4. **分析上游产品价值**
   - JTBD：用户是谁、在什么场景、多久一次、痛点严重度。
   - 替代品：系统自带功能、付费 App、Tina 现有功能。
   - 产品验证信号：issue 情绪、release 频率、是否有付费/企业版、是否有明确迁移诉求（只引用可核实的事实）。
   - 区分“产品本身有价值”和“这个开源实现值得借鉴”。

5. **分析 Tina 增量收益**
   - 新增能力：Tina 用户以前做不到什么，现在能做到什么。
   - 协同：能否复用现有服务、权限、菜单栏/面板/Island 入口。
   - 替代：能否少装一个付费/常驻 App。
   - 代价：权限、私有 API、维护面、支持成本、与现有功能的冲突。
   - 结论必须能回答：“为这个功能增加 1 MB 和 1 个权限，值不值？”

6. **给决策，而不是只给清单**
   - `pursue`：直接做完整版。
   - `MVP`：只做高价值子集，列出第一版不做什么。
   - `defer`：价值成立但当前成本/风险不成立，写清触发条件。
   - `reject`：违反硬约束、重复或价值不足。
   - 每个决策附 1–3 条证据；不确定的地方明确写“unknown”。

7. **按 feature issue 格式产出报告**
   - 使用 `references/report-template.md`，字段与 `.github/ISSUE_TEMPLATE/feature_request.yml` 对齐。
   - 额外增加“开源调研结论”小节，写清约束检查、价值评分和 MVP 边界。
   - 默认只输出报告；只有在用户明确要求“提 issue”时才执行 `gh issue create`，并先给出标题、标签和正文摘要。

## 价值评分（1–5，写理由）

| 维度 | 5 | 3 | 1 |
|---|---|---|---|
| 上游产品价值 | 明确的高频刚需，用户愿意付费/迁移 | 有用的利基功能 | 演示性/一次性需求 |
| Tina 用户收益 | 新增核心能力或替代付费 App | 增强现有功能 | 边际改进 |
| 契合度 | 复用现有架构/入口/权限 | 需要少量新服务 | 新子系统/新运行时 |
| 实现成本（反向） | S，1–3 天 | M，1–2 周 | XL，1 个月以上 |
| 风险（反向） | 无新权限/私有 API | 可控的私有 API/权限 | 特权 helper/系统扩展/不稳定 API |

排序时以“用户收益 / 成本”优先，不以 star 数或功能数量排序。

## 必须避免

- 把上游的功能列表原样搬过来，不判断重复和复杂度。
- 用 star 数、下载量代替用户价值分析。
- 忽略上游 Release 包体积，或用 Tina 的包体大小、star 数代替；也不要用“压缩后可能更小”搪塞。
- 把“没有 release”当成体积不合格；这种情况应跳过该判据。
- 忽略 macOS 14 兼容性；Tina 当前最低版本是 14。
- 建议引入 Electron/Node/Python 运行时。
- 为了一个功能引入新的特权 helper 或系统扩展而不给安全/维护分析。
- 编造用户量、性能提升、付费意愿等无法核实的指标。
- 直接复制上游代码或界面；本 skill 只提取产品行为，代码按 Tina 架构重写。
- 派 agent 打开或截图目标 App 获取调研证据；截图可能让宿主系统卡死，只使用 README、文档、release notes、issue 等文本来源。
