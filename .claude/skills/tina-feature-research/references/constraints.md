# 硬约束判定细则

## 1. macOS 15

检查顺序：

1. 上游项目的最低系统版本：`MACOSX_DEPLOYMENT_TARGET`、`Package.swift` 的 `platforms`、`Info.plist` 的 `LSMinimumSystemVersion`、README/Release notes。
2. 功能使用的 API 是否 macOS 15+；如果是，Tina 当前最低 14 的构建需要：
   - `if #available(macOS 15, *)` 版本门控，14 上隐藏入口；
   - 或明确接受把 Tina 最低版本提升到 15（必须单独说明影响）。
3. 如果是 Linux/Windows 为主的实现，确认它的 macOS 版本是否被“顺带支持”，不要把“有 macOS 构建”当作“在 15 上可靠”。

结论写法：

- `macOS 15: pass`：功能在 15 可用，14 有明确降级/隐藏方案。
- `macOS 15: conditional`：15 可用，但 14 需要门控，列为待确认。
- `macOS 15: fail`：依赖 16+ API 或无法在 15 运行。

## 2. 原生实现

优先顺序：

1. Swift / SwiftUI / AppKit / Objective-C 原生；
2. 小型 C/C++/Rust 核心 + Swift 外壳，且能说明二进制体积和构建复杂度；
3. 不接受的默认项：Electron、Node、Java、Python、Go 运行时、WebView 作为主界面。

如果是非原生项目，问题不是“能不能重写”，而是“重写后是否仍能在预算内交付”。必须给出：

- 需要重写的模块；
- 可以丢弃的模块；
- 预计代码量（S/M/L/XL）；
- 是否引入第三方依赖。

## 3. Release 体积（≤30 MB）

Tina 当前完整 DMG 约 28 MB，因此：

- **默认新增预算：1–2 MB**；
- 单个功能超过 2 MB 必须给出理由，并说明是否可以通过按需下载、资源压缩、移除旧资源抵消；
- 不允许把“模型/词典/图标/媒体资源”直接塞进主包而不估算压缩后体积。

估算方法：

1. 上游 release 产物大小只作参考，不能直接等同 Tina 增量。
2. 统计目标功能会新增的：
   - 二进制/框架（未压缩 → 压缩后大致 40–60%）；
   - 资源（图片、音频、模型、数据库）；
   - 第三方依赖；
   - 本地化字符串（通常可忽略，但 15 种语言要算）。
3. 给出区间和不确定性，例如“新增 0.6–1.2 MB（主要是 2 个图标集和 ~200 KB 配置）”。
4. 如果估算超过预算，给出降级方案：只做核心子集、资源按需下载、复用现有资源。

结论写法：

- `size: pass`（估算 ≤1 MB）
- `size: conditional`（1–2 MB，需要压缩/裁剪）
- `size: fail`（>2 MB 且无抵消方案）

## 4. 复杂度

以下任一出现，默认降级为 `defer`/`reject`，除非用户价值极高且风险有缓解：

- 新增特权 helper、LaunchDaemon、系统扩展、DriverKit、网络扩展；
- 新增常驻后台服务或独立 agent；
- 需要关闭 SIP、修改系统文件、注入其他进程；
- 依赖不稳定的私有 API，且没有降级路径；
- 需要维护一套新的同步/账号/云服务；
- 功能本身是一个完整子系统（如新的窗口管理器、新的浏览器、新的 AI 运行时）。

允许的例外必须写：

- 为什么现有公开 API 做不到；
- 失败/权限被拒时的降级行为；
- 卸载/关闭时如何彻底清理；
- 维护成本由谁承担。

## 5. 不重复现有功能

先查：

- `Sources/Tina/Core/FeatureCatalog.swift`：已有功能清单和分组；
- `Sources/Tina/Services/`：已有服务能力；
- `README.md`：对用户承诺的能力；
- `gh issue list --repo zbl-jerry/tina --state all`：已有需求。

判定：

- `duplicate`：现有功能已经覆盖同样用户任务，直接 reject/合并到已有功能。
- `enhancement`：现有功能只覆盖一部分，说明新增的是哪一段行为。
- `new`：现有功能完全不覆盖。

注意：同一能力的“另一种 UI”不算新功能；同一能力的“自动化/日程/跨设备”可能是增强。

## 6. 用户价值

至少回答：

- 谁在什么场景下用？
- 没有它时用户现在怎么做（系统功能/付费 App/手工操作）？
- 使用频率和痛点严重度？
- Tina 用户获得的是“新能力”“少装一个 App”“现有功能更好用”中的哪一种？
- 如果只能做 20% 的功能，哪 20% 保留最多价值？

不要把 star 数、下载量、README 的营销语当作价值证据；引用具体 issue、release note、可复现的用户任务。

## 7. 决策阈值

| 结论 | 条件 |
|---|---|
| pursue | 硬约束全过；用户收益 ≥4；成本 ≤M；风险可控 |
| MVP | 硬约束全过；完整版成本/体积过高，但核心子集收益 ≥4 |
| defer | 价值成立，但当前受体积/权限/复杂度/依赖限制；写清触发条件 |
| reject | 违反硬约束、重复、价值 <3，或无法在 Tina 架构内维护 |
